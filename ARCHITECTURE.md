# Architecture

`polars_bt` contains three independent backtesting engines exposed as Polars
expression plugins in one Rust extension. They share the Python package, PyO3
module, and Polars allocator. Mosaic and Tempo also share diagnostic formatting
and the Polars verbose setting; portfolio and execution state remain separate.

```text
polars_bt/
├── pulse.py              # T0 expression wrapper
├── mosaic.py             # daily portfolio expression wrapper
└── tempo.py              # timestamp portfolio expression wrapper
src/
├── lib.rs                # Python module and global allocator
├── diagnostics.rs        # shared verbose setting and diagnostic records
├── pulse/                # quote matcher, orders, and T0 position state
├── mosaic/               # daily state, engine, output, and diagnostics
└── tempo/                # timestamp state, engine, validation, and output
```

## Python and Rust boundary

The public functions return `polars.Expr` objects using
`register_plugin_function`. Polars loads the native functions generated by
`pyo3-polars` and passes Series through its plugin FFI. All engines execute in
the Polars process, without serializing a DataFrame through Arrow IPC. The
extension uses `PolarsAllocator` as its global allocator.

Wrappers accept column names or expressions and cast inputs to the Rust types.
Mosaic and Tempo convert numeric nulls to NaN; Rust rechunks these numeric inputs
before borrowing contiguous slices. NaN weights mean zero target, NaN returns
mean zero return, and NaN or non-positive Mosaic prices prevent execution.
Boolean nulls are rejected. Tempo also casts timestamps to microsecond Datetime,
derives the trade date, and casts asset identifiers to String.

Callers construct, sort, and materialize complete panels. The wrappers do not
fill missing assets or reorder rows. All three plugins are non-elementwise:
Pulse declares a scalar result, while Mosaic and Tempo declare that they change
length. Portfolio expressions are intended for eager whole-table execution.
Polars 2.0 defaults lazy collection to streaming, while eager DataFrame
operations retain in-memory execution. Materialize preprocessing results and
explicitly sort by time and asset before executing the plugin; joins and
group-by operations may change row order. This does not add direct streaming
backtest support.

## Pulse

Pulse consumes quote and signal columns in time order. Its exchange, matcher,
order, and position types are isolated under `src/pulse`; it returns one Struct
summary for the complete input. The summary contains position and win counts,
signal count, floating PnL, and realized PnL.

Pulse expects non-empty input with valid quotes, time indices, and first-row
price limits. Null signals are treated as inactive. It currently does not
validate all other null or shape errors before indexed access.

## Mosaic

Mosaic consumes a materialized date-major panel. Callers guarantee that every
date has `asset_num` rows in the same asset order. Rust therefore
uses fixed row slices and a holding vector, with no joins, asset IDs, hashing, or
Arrow IPC serialization.

For each day the engine applies:

1. overnight returns;
2. daily turnover reset;
3. eligible sells;
4. eligible buys in stable row order using captured cash and a strict `<` limit;
5. intraday returns;
6. turnover finalization and snapshot;
7. negative-cash stop after the snapshot.

The result has one Struct row per completed day: `date`, `cash`, `nav`,
`turnover`, and `holding_count`. The date retains its input type.

Rust validates input lengths, positive `asset_num`, and finite non-negative
fees. It cannot validate asset identity or cross-day asset order because asset
identifiers are absent from this interface. Verbose diagnostics can report
inconsistent date blocks or rebalance flags, but do not repair the panel or
change execution. A negative-cash stop preserves the final snapshot and
truncates later days.

## Tempo

Tempo consumes a materialized datetime-major panel. The first timestamp defines
the canonical asset vector. Rust rejects duplicate assets, incomplete later
blocks, changed asset order, non-increasing timestamp blocks, or mixed rebalance
flags within a block. It also rejects negative weights and infinite weights or
returns; numeric nulls retain the NaN semantics described above.

For each timestamp the engine releases T+1 holdings when the derived date
changes, applies `period_ret` to existing holdings, and optionally rebalances.
Eligible sells precede buys. Buys use stable row order, captured available cash,
and the same strict `<` cash limit as Mosaic. With `t1=True`, purchases become
sellable on a subsequent date; `t1=False` allows same-day sales. A timestamp
without rebalancing still marks holdings and emits a snapshot.

The result has one Struct row per timestamp: `datetime`, `cash`, `nav`,
`turnover`, and `holding_count`. Turnover is measured for that timestamp.
Tempo is long-only and tracks sellable holdings separately from total holdings.

## Diagnostics

Mosaic and Tempo use the shared `POLARS_VERBOSE` setting and write bounded
diagnostic records to stderr. The setting is refreshed at each execution so
`pl.Config.set_verbose()` and its context manager take effect after import.
Input reports retain counts and first locations rather than per-row logs.
Non-finite portfolio state remains a hard error regardless of verbosity.
Pulse retains its separate explicit `verbose` argument.

## Compatibility boundary

The supported combination is CPython 3.10–3.12 and Python Polars
`>=2.0.0,<2.1` with Rust Polars 0.55.2, `pyo3-polars` 0.28.0, and PyO3 0.29.
Polars 2.0 retains the version-0 plugin FFI used by this Rust dependency stack;
the Rust crate versions therefore remain unchanged. Both the 2.0 verification
and historical 1.44 migration are recorded in [the upgrade analysis](docs/polars-upgrade.md).

PyO3's `abi3-py310` feature covers the Python extension ABI. It does not make the
Polars plugin ABI independent of the host Polars version. Python dependency
bounds, Rust Polars, `polars-config`, `pyo3-polars`, and the rebuilt native
extension must be reviewed and validated together. Python import alone does
not exercise the plugin FFI; compatibility checks must execute all three
expressions and verify their output schemas and reference results.
